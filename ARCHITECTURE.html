ProRag backend architecture · plain-english guide

A document engine that shows its work

Ask a question. Get an answer you can check.

ProRag reads your documents — PDFs, Word files, slide decks, spreadsheets — and answers questions about them in plain language. The part that matters: every sentence it writes points back to the exact page it came from, so you can open the document and see for yourself.

§ 1

The whole system in one picture

There are only two things you can do with ProRag: put a document in, and ask a question. Everything in the codebase serves one of those two jobs, and they meet in the middle at the database.

Why one database? Text search, meaning search and spreadsheet rows normally need three separate systems. ProRag runs all three inside PostgreSQL, so there is one thing to back up, one thing to secure, and one thing that can break.
§ 2

Getting documents in

A computer cannot search a PDF the way you read one. Before a document is useful it has to be taken apart, cut into pieces small enough to quote, and turned into numbers. That is what happens when you upload a file.

  1. Check it before touching the disk

    The file is read in one-megabyte pieces and rejected the moment it crosses 100 MB — so an oversized upload never fully lands in memory. Then ProRag looks at the file's first few bytes and compares them to the file extension. A virus renamed notes.pdf is refused here, because its contents say otherwise.

  2. Notice if you've uploaded it before

    Every file gets a SHA-256 fingerprint. If that fingerprint already exists, ProRag returns the original document instead of storing a second copy. This check happens before the file is written, so a re-upload costs nothing at all.

  3. Read it with the right tool

    Spreadsheets and CSVs go to pandas. PDFs, Word files and slide decks go to Docling, which understands layout — it can tell a heading from a paragraph from a table, and reports where on the page each one sits. If Docling is not installed or chokes on a file, ProRag quietly falls back to PyMuPDF, which extracts plain text. Plain .txt and .md skip straight through.

  4. Cut it into quotable pieces

    Text is packed into chunks of roughly 700 words, with 100 words of overlap so a sentence split across a boundary still appears whole somewhere. Crucially, a chunk never spans two pages and never crosses a heading — otherwise a citation could not point at a single place. Each chunk also carries a breadcrumb of the headings above it, which helps the search understand context.

  5. Turn every piece into numbers

    Each chunk is sent to an embedding model, which returns a long list of numbers describing what it means. These are sent in batches of 64, four batches at a time. If the provider times out or rate-limits, ProRag waits and retries with growing delays — but only for problems that might fix themselves. A malformed request is not retried.

  6. Publish it — or record why it failed

    The document sits at processing the whole time, and search deliberately ignores anything not marked ready, so a half-finished document can never appear in an answer. If any step fails, the document is marked failed with a short, cleaned-up reason — provider errors can contain API keys and URLs, so the raw message is never stored.

Tables get special treatment

A table turned into ordinary sentences becomes useless — "the 2024 column says 47" loses its meaning once flattened. So every table is stored three separate ways, and searches can hit whichever version fits the question.

Version 1 — the gist

A summary. "Table: Inspection log. Columns: vessel, date, result. 240 rows," plus the first three rows as an example. Good for "is there a table about X?"

Version 2 — the blocks

Row windows. The table sliced into blocks of about 25 rows, each block repeating the header row so it still makes sense on its own. Good for reading a range.

Version 3 — the records

One chunk per row, written as vessel: X | date: 2026-03-01 | result: pass. Used for wide tables (more than 12 columns), where a row reads better as a record than a line.

And a fourth copy, for exact lookups. Every row is also saved as raw structured data, so ProRag can answer "show me rows where status = failed" precisely, rather than hoping a similarity search happens to surface it.
§ 3

Finding the right passage

This is the part that decides whether an answer is good. A language model can only work with what it is handed — so the real job is narrowing thousands of chunks down to the handful that actually matter. ProRag does that in six stages, each one throwing away more than the last.

You ask one question
1 question
A small model rewrites it two ways
2 searches
Each search runs three different ways
240 candidates
Merged into one list, duplicates collapsed
~150 after dedupe
A slower, smarter model re-reads the top ones
40 re-scored
Trimmed to only what's clearly relevant
3–12 ≤ 6,000 words

Bars are drawn to scale; the merge step varies by question, since the three searches often find the same passage. The model that writes your answer sees only the last row — roughly 5% of what was found, and none of the rest.

Stage 3, up close: three ways to search at once

No single search method is reliable on its own. Each of these is good at something the others are bad at, so ProRag runs all three and lets them vote.

Arm 1 — by meaning

Compares the question's numbers to every chunk's numbers and finds the closest. Catches "how often do we test the alarms?" matching a passage about fire drill frequency — no shared words at all.

Weakness: vague about exact terms. Product codes and names slip past it.

Arm 2 — by words

Classic keyword matching, scored by BM25 — the same family of ranking used by search engines. Nails exact phrases, part numbers, and rare words.

Weakness: blind to synonyms. Ask about "cars", miss every mention of "vehicles".

Arm 3 — by row

Looks inside spreadsheet rows for exact values. Only switches on when the planner decides the question is about tabular or numeric data.

Given extra weight (1.2×) — when it fires at all, an exact row match is usually the right answer.

How the votes are counted. The three arms produce scores that mean completely different things — you cannot average them. So ProRag ignores the scores entirely and looks only at position: a chunk ranked 1st, 3rd and 2nd across three lists beats one ranked 2nd in a single list. This is called Reciprocal Rank Fusion, and it is why one arm having a wildly inflated score cannot hijack the result.

Stages 5 and 6: the two cleanups that matter most

Stage 5 — re-reading

The first three searches are fast because they compare pre-computed numbers. The reranker is different: it reads the question and the passage together, which is far more accurate and far slower. Running it on 40 candidates is affordable. Running it on thousands would not be.

If the reranker model isn't installed, this stage is skipped silently and the existing order stands — a missing extra never breaks the system.

Stage 6 — trimming

Rather than always taking a fixed top-10, ProRag looks at the gap: anything scoring more than 0.15 below the best result is dropped. A question with one clear answer gets three sources; a broad question gets twelve.

It also spots repeats. "Safety Manual Rev 3" and "Safety Manual (May 2021)" are recognised as the same document, and only the newer one survives — so the model isn't shown the same rule twice and cannot contradict itself.

§ 4

Writing the answer, live

The shortlist is numbered [S1], [S2], [S3] and handed to a language model with strict instructions: answer only from these blocks, mark every claim, and say so plainly if the answer isn't here.

What the model actually receives

Context:
[S1] Safety Manual — p.14
Fire drills shall be conducted at
intervals not exceeding one month…

[S2] Inspection Log — p.3
| vessel | date       | result |
| MV Ora | 2026-03-01 | pass   |

Question: How often are fire drills required?

Simple by design. The numbering is the entire mechanism — the model writes [S1], and ProRag knows precisely which page that refers to.

What comes back, in order

  • sources

    Sent before the first word of the answer — every source the model can see, not just the ones it ends up quoting. You get to judge the evidence before the conclusion.

  • token

    The answer, word by word, as it's written.

  • citation

    Fires the instant a new [S1] appears, so the matching source can light up mid-sentence.

  • meta

    IDs for the message and conversation, plus the final list of what was cited.

  • done

    Finished. Or error, if something broke — never a connection that just goes quiet.

Three problems with streaming, and how each is handled

Half-drawn tables

Sent word by word, a table row appears as a broken jumble before it completes. So any line starting with | is held back until its line ends, then released whole.

Models that get stuck

Occasionally a model falls into emitting blank space forever. After 200 consecutive whitespace characters ProRag cuts the stream and appends a visible truncation note, rather than hanging.

Proxies that hang up

A quiet connection looks dead to a proxy. Every 15 seconds of silence, ProRag sends an invisible keep-alive. Compression is also skipped for streams — compressing a stream would buffer it and defeat the point.

§ 5

Why you can trust the citations

A citation is only worth something if it cannot be faked. Three rules make these real.

Rule 1 — tidy up the markers

Models drift. They write (S1), [s1], [source 1] or plain [1]. All of these are rewritten to one canonical form before anything else happens, so a stylistic wobble never becomes a broken link.

Rule 2 — invented sources are dropped

If the model cites [S9] when only five sources were supplied, that reference is discarded rather than shown. A citation that points nowhere is worse than no citation.

Rule 3 — show the evidence, not the summary

During streaming, you're shown everything the model was given — including passages it chose not to use. Showing only what it quoted would let it hide the context that disagreed with it.

From a marker to a highlighted page

Each stored citation keeps the document, the page number, and — when the layout parser was available — a bbox: the four coordinates of the rectangle on that page. That is what lets a viewer open the PDF, jump to the page, and draw a box around the exact sentence.

Citations are saved as their own rows in the database, one per marker, rather than as a blob of text inside the message. Which means the question "which documents does this answer actually rest on?" is a query, not a parsing exercise.

§ 6

Money, keys and staying up

Every question costs real money at a provider. These are the guards that stop a bad day from becoming an expensive one.

Spending

A daily ceiling, checked before spending

Every call — planning, embedding, answering — writes a row recording its tokens and cost. Before any request touches a provider, ProRag sums today's spend; past the cap (£/$5 by default) it returns a refusal without spending another cent.

Checking first rather than after is the entire point: a runaway loop is stopped at the door, not billed and then reported.

Access

Keys that can't leak from the database

API keys are stored only as fingerprints. The real key is shown once, at creation, and never written down — so even a full copy of the database hands an attacker nothing usable.

Keys can be limited to a single collection of documents. Authentication is off by default for local development, so the UI works out of the box.

Health

Two different health questions

/healthz asks "is the process alive?". /readyz asks the harder question — "can it actually serve traffic?" — by querying the database with a 5-second limit.

The limit matters. Without it, an overloaded server would hang instead of answering, and a load balancer would read that as broken rather than busy. Database errors are never echoed back, since they can contain connection details.

Capacity

Letting go of the connection early

Searching opens a database connection. Writing the answer takes several seconds. Holding that connection through the whole answer would let roughly ten simultaneous chats exhaust the pool.

So ProRag closes the transaction the moment searching finishes, before calling the language model. Same work, a fraction of the contention.

§ 7

Checking that it actually works

"The answers seem good" is not a measurement. ProRag keeps a set of known questions with known correct answers, and can re-run the whole pipeline against them on demand.

MeasureThe question it answersNeeds extras?
Hit rate Did the right document survive all six stages and reach the model at all? No
Keyword coverage Does the answer contain the facts it was supposed to contain? No
Citation validity Does every marker the model wrote point at a source that genuinely existed? No
Faithfulness Is the answer actually supported by the passages, or partly invented? ragas
Answer relevancy Does it address the question that was asked? ragas
Context precision Was the shortlist mostly useful, or padded with noise? ragas
The first three always run. The deeper metrics need an optional library, and if it isn't installed the run simply reports them as skipped instead of failing. Every run is saved with its per-question detail, so two runs can be compared after a change — which is the only way to know whether a tweak to the search actually helped.

Eleven tables, in four groups. Deleting a document cleanly removes everything beneath it.

The four indexes doing the heavy lifting

HNSW · meaning search

Finds near-matching numbers without comparing against every chunk. Automatically switches to a half-precision variant for very large embedding models, which would otherwise exceed the index's limit.

BM25 · word search

Provided by ParadeDB. If the extension is missing, ProRag detects it once at startup and falls back to PostgreSQL's built-in text search — same pipeline, slightly blunter ranking.

GIN · row search

Makes looking inside spreadsheet rows fast, so exact-value questions don't require scanning every row of every table.

Generated column · always current

The searchable form of each chunk's text is computed by the database itself, so it can never drift out of sync with the text it describes.

§ 10

Running it

Three containers. One command.

Container 1

ParadeDB

PostgreSQL with the vector and BM25 extensions already built in. This is the only container holding state — everything else can be destroyed and rebuilt freely.

Container 2

The API

FastAPI on uvicorn. Waits for the database to report healthy before starting, so a cold boot doesn't produce a crash loop.

Container 3

Caddy

Sits in front and handles HTTPS certificates automatically — no manual certificate renewal to forget about.

Schema changes are versioned. Seven migrations take the database from empty to current, in order. Upgrading a running deployment means running them, not editing tables by hand — and the same sequence runs identically on a laptop and in production.

Designed to degrade rather than break

A recurring pattern worth naming: every optional piece has a fallback, so a missing dependency reduces quality instead of causing an outage.
